# Web agent tools

Read-only views of the web agent: tasks and their approval state, the commit classifier, stats, browser sessions, secure-fill session counts. No clicks, approvals or fills.

Generated by `tool gen` from packages/tools (domains/web.py): edit the registry, not this file. MCP server `hub` (tool `mcp__hub__<MCP name>`) and `tool call NAME '<json>' [--json]` run the same gateway and return the same result. Every input also takes `format`: concise (default) | detailed. Errors: {code, message, hint}; codes invalid_args, not_found, conflict, unavailable, timeout, rate_limited, approval_required, failed, internal. Each call logs one usage event (via=gateway, trace id, ms, code).

## web.tasks

Web tasks (open ones by default, all, or one by id) with their state, waiting step and result.
States: running, pending = his ✅ card is out, approved, done ... For "is my booking through", resuming or
checking a task.

Input:
- `id` (string /^wa[0-9a-f]{6}$/ (optional)): one task (wa + 6 hex)
- `all` (boolean): also finished tasks (default: open ones)

Output: `count`, `tasks`
Example: `tool call web.tasks '{}'`
Example: `tool call web.tasks '{"all": true}'`

## web.check

Is clicking a control with this label a committing step (pay, book, order, delete, cancel, submit)?
The same classifier the commit gate uses. true = stop before it: only his ✅ on the approval card lets it run.

Input:
- `label` (string, required): a button or link label, e.g. 'Pay now'

Output: `commit`, `tier`, `category`, `matched`, `exempt`
Example: `tool call web.check '{"label": "Pay now"}'`
Example: `tool call web.check '{"label": "Next"}'`

## web.stats

Web agent numbers: tasks, completions, commits, approval cards and approvals, guard blocks.
Also the median approval time and the abandon rate.

Input:
- `days` (integer, default 30)

Output: `stats`
Example: `tool call web.stats '{}'`
Example: `tool call web.stats '{"days": 7}'`

## web.sessions

Browser sessions (abx: one pinned window + tab per agent) with their web task, idle time and tab state.
With task: that task's session ids (for resuming it).

Input:
- `task` (string /^wa[0-9a-f]{6}$/ (optional)): only this web task's sessions

Output: `count`, `sessions`
Example: `tool call web.sessions '{}'`
Example: `tool call web.sessions '{"task": "wa0a1b2c"}'`

## web.fill_status

Secure fill at a glance: live fill sessions, vault requests waiting for his ✅, redaction count.
Counts and states only: never a value.

Input:
- (none)

Output: `sessions`, `pending_requests`, `live_fingerprints`, `psp_hosts`, `site_profiles` (concise leaves out site_profiles)
Example: `tool call web.fill_status '{}'`

## web.fill_session

A web task's fill session: state, minutes left, which of his fields were released and how often.
Names and counts only. Starting one is `webagent start --data yes` / securefill (his ✅ in the vault bot), not a
tool.

Input:
- `id` (string /^wa[0-9a-f]{6}$/, required): the web task id

Output: `state`
Example: `tool call web.fill_session '{"id": "wa0a1b2c"}'`

## CLI and cron

`webagent` / `abx` / `securefill` (CLIs; skill web-agent; tests ~/opt/webagent-tests, ~/opt/agent-browser/tests): the whole task protocol stays there and with the browser subagent: start, step, stop (the approval card), approve (his ✅ only), resume, done, abort; abx start/stop and page commands; securefill session start, fill, commit, tick, mask, shot. None of those is a tool: the commit gate (webagent-guard, abx's built-in gate) and the vault's ✅ for his data stay the only way to act on a page.
