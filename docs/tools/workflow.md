# Workflows tools

Durable workflows and schedules on the hub (DBOS): start, read, message and cancel workflows (web-task approval waits, probes), list and edit the watch schedules; the executor side of a scheduled watch job.

Generated by `tool gen` from packages/tools (domains/workflow.py): edit the registry, not this file. MCP server `hub` (tool `mcp__hub__<MCP name>`) and `tool call NAME '<json>' [--json]` run the same gateway and return the same result. Every input also takes `format`: concise (default) | detailed. Errors: {code, message, hint}; codes invalid_args, not_found, conflict, unavailable, timeout, rate_limited, approval_required, failed, internal. Each call logs one usage event (via=gateway, trace id, ms, code).

## workflow.start

Start a durable workflow on the hub; it survives hub and brain restarts. webtask.approval = a web task's
approval wait (webagent starts it); hub.probe = a smoke test that waits for one "ping".

Input:
- `name` (webtask.approval | hub.probe, required): which workflow
- `args` (object): its arguments (webtask.approval: task, stop, nonce, ttl, notify; hub.probe: ttl)
- `id` (string /^[A-Za-z0-9][A-Za-z0-9:._+-]{0,127}$/ (optional)): workflow id; the same id again = the same run

Output: `id`, `name`, `status`, `created`, `updated`, `output`, `error`, `recoveries`, `events` (concise leaves out created, updated, recoveries, events)
Example: `tool call workflow.start '{"name": "hub.probe", "args": {"ttl": 30}}'`

## workflow.status

Read workflows on the hub: one by id (with its events, e.g. a web task's waiting.until and outcome) or the
newest ones, filtered by name and status. For "is the approval wait still running", "did the watches run".

Input:
- `id` (string /^[A-Za-z0-9][A-Za-z0-9:._+-]{0,127}$/ (optional)): one workflow (with its events); none = a list
- `name` (webtask.approval | hub.probe | job.tick (optional))
- `status` (PENDING | ENQUEUED | SUCCESS | ERROR | CANCELLED (optional))
- `limit` (integer, default 20)

Output: `runs`
Example: `tool call workflow.status '{}'`
Example: `tool call workflow.status '{"name": "webtask.approval", "status": "PENDING"}'`

## workflow.send

Send a message to a waiting workflow (DBOS send: kept until its recv takes it, across restarts).
webtask.approval reads {"decision": approved|declined|stopped|replaced|cancelled} on topic "decision".

Input:
- `id` (string /^[A-Za-z0-9][A-Za-z0-9:._+-]{0,127}$/, required)
- `topic` (string /^[a-z][a-z0-9_.-]{0,39}$/, required): e.g. "decision" (webtask.approval), "ping"
- `message` (object | string | integer | boolean (optional))
- `key` (string /^[A-Za-z0-9][A-Za-z0-9:._+-]{0,127}$/ (optional)): idempotency key: a resend with it lands once

Output: `sent`, `id`, `topic`
Example: `tool call workflow.send '{"id": "webtask:abc123:1", "topic": "decision", "message": {"decision": "approved"}}'`

## workflow.cancel

Cancel a workflow on the hub (it stops at its next step; DBOS keeps the record).

Input:
- `id` (string /^[A-Za-z0-9][A-Za-z0-9:._+-]{0,127}$/, required)

Output: `id`, `name`, `status`, `created`, `updated`, `output`, `error`, `recoveries`, `events` (concise leaves out created, updated, recoveries, events)
Example: `tool call workflow.cancel '{"id": "hub-probe-0a1b2c3d4e5f"}'`

## workflow.schedules

The hub's job schedules (DBOS) and the schedule registry (core/schedules.toml: every periodic job, its class,
queue, runner and why). Default: the live schedules (job, mode shadow|live, cron, status, last fire; runs>0 adds
their newest runs). registry=true (or cls) lists registry jobs with their schedule state; job= shows one.

Input:
- `runs` (integer): also each schedule's last N runs (detailed shows them)
- `job` (string /^[a-z0-9][a-z0-9-]{0,39}$/ (optional)): show one registry job (its entry + schedule)
- `registry` (boolean): list the registry (core/schedules.toml), not only schedules
- `cls` (W | X | T | C | V | M | R | K (optional)): registry class

Output: `schedules`, `jobs`
Example: `tool call workflow.schedules '{}'`
Example: `tool call workflow.schedules '{"runs": 3}'`

## workflow.schedule

Add, edit, pause, resume, remove or fire one job's schedule on the hub (any registry job that can move; its
queue and time limit come from the registry). live runs the job for real: only once its cron line is gone (`hub
wf cron` lists them), or it runs twice. Every change takes a why and shows in the agenda.

Input:
- `job` (string /^[a-z0-9][a-z0-9-]{0,39}$/, required): a registry job (core/schedules.toml: watch, train-watch, ...)
- `state` (shadow | live | edit | paused | active | absent | run, required): shadow/live = add or replace in that mode · edit (new cron, mode kept) · paused · active (resume) · absent (remove) · run (fire once now)
- `why` (string, required): why (shows in the agenda as schedule.changed)
- `cron` (string (optional)): override the job's cron (default: its registry cron)

Output: `name`, `job`, `mode`, `cron`, `tz`, `status`, `last_fired`, `queue`, `timeout`, `catch_up`, `runs` (concise leaves out runs, tz, queue, timeout, catch_up)
Example: `tool call workflow.schedule '{"job": "watch", "state": "live", "why": "watch runs from the hub"}'`
Example: `tool call workflow.schedule '{"job": "drive-watch", "state": "paused", "why": "wedding drive day"}'`

## workflow.job

Run one registry job here as its cron line would (a hub schedule calls this; the brain may too). shadow (the
default) only says what it would run. A failure streak of `after` runs emits one job.failed event, the next
good run job.recovered (cron-fail's semantics); each live run of a job with after > 0 also writes cron-fail's
usage run row (job.<name>), a shadow tick none. Some jobs text him once per event (hence send_owner). The job's
time limit is its registry timeout, or timeout_s when that is shorter (a hub schedule passes how long it waits).

Input:
- `name` (string /^[a-z0-9][a-z0-9-]{0,39}$/, required): the registry job (core/schedules.toml)
- `mode` (shadow | live, default "shadow"): shadow = only say what would run
- `slot` (string (optional)): the schedule's fire time (for the log)
- `timeout_s` (integer (optional)): how long the caller waits (s): the job ends by then at the latest

Output: `job`, `mode`, `exit`, `secs`, `would_run`, `event`
Example: `tool call workflow.job '{"name": "watch"}'`

## workflow.window

An event window's tick (the hub's event.window clock, once a minute while it is open): eventwf starts the
registry jobs due at that minute and says whether the window is still open.

Input:
- `kind` (night | party | drive | sleepin, required): the window's kind
- `key` (string /^[A-Za-z0-9@._:+-]{1,120}$/, required): the brain's key for the window
- `at` (integer, required): the tick's minute slot (epoch s)

Output: `kind`, `key`, `decision`, `ran`, `next_s`, `late_s`
Example: `tool call workflow.window '{"kind": "night", "key": "abc@2026-10-24", "at": 1792000000}'`

## CLI and cron

`hub wf` (CLI): `hub wf status`, `hub wf engine on|off`, `hub wf ls`, `hub wf show ID`, `hub wf watches shadow|live|off [--jobs a,b]` (live refuses while the jobs' cron lines are still in ~/crontab), `hub wf cron` (which cron lines the watch schedules replace, and the lines the registry does not know). The registry is core/schedules.toml (`assistant cron check|tag`). Engine off = every tool here answers unavailable.
